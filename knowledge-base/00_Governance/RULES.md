# RULES.md

本文件只定义 {KB_ROOT} 的知识库治理、身份归属、主 RUN 留痕和读写规则。通用授权、Git、工程质量、角色 Skill 和验证层级以当前有效的全局 AGENTS.md 为准；项目事实以当前项目入口与当前物理证据为准。

## 1. 权威顺序与低 Token 启动

用户当前对话中的明确目标、授权和更正优先。`{KB_ROOT}\AGENTS.md` 是唯一精确启动序列；本文件不再复制该序列。进入项目后先以 `START_HERE.md` 建立当前边界，只有信息不足时才按入口定向补读；阶段接力只增加当前合同和该 `MILESTONE_ID` 的精确 `MASTER_RUN`。

优先精确路径、标题、状态码和 `rg` 定向检索。不得默认扫描整个知识库、全部项目、全部 RUN、完整历史、旧聊天或真实工程；历史只能补充当前证据，不能覆盖当前入口和当前物理证据。

无法根据保存项目、项目 ID、路径和当前上下文唯一识别项目时，询问一个最小问题，不得猜测或混用相似项目。项目目录不存在时，暂停真实工程执行并询问是否创建。普通问答、翻译、提示词、话术和用户已完整提供内容的分析不机械启动项目治理。

## 2. 目录与文件职责

- 00_Governance：知识库治理、跨项目稳定规则和治理主 RUN。
- 01_Projects：各项目当前事实、状态、待办、风险、经验和主 RUN。
- 02_Knowledge：跨项目接口、测试、发布、排障和专题知识。
- 03_Agent_Outputs：原始输出、长报告和待提炼材料，不直接作为当前事实。
- 99_Archive：过时、冻结或压缩前版本；归档写明时间、来源和原因，不删除审计链。

项目文件职责：

- START_HERE.md：低 Token 当前入口，只保留项目定位、当前状态、允许/禁止、关键路径、必要阅读、下一关和特别提醒。
- PROJECT.md：项目定位、范围和长期边界。
- PATHS.md：路径与环境；记录路径不代表访问授权。
- STATUS.md：当前已确认事实和阶段状态。
- TODO.md：当前待办、阻断和待验证事项。
- DONE.md：有对应证据的完成项。
- RISKS.md：当前风险、影响、置信度和缓解方向。
- FAQ.md：有来源的稳定问答。
- CHANGELOG.md：重要状态/结构变化摘要，不保存逐轮流水。
- LESSONS.md：经提炼且可复用的踩坑和防复发规则。
- RUNS\YYYY-MM：每个完整目标或里程碑的一份主 RUN。
- AGENT_NOTES.md：兼容旧记录；新工作不默认追加流水。

## 3. 读写与授权边界

知识库中的工程、样本、运行包、发布目录、数据库、硬件和服务路径只证明位置，不授权读取、扫描、修改、构建、运行、连接、发布、Git、MES 或生产操作。

“工程只读/只审查/不改源码”禁止真实工程修改，但若未禁止知识库写入，目标完成或硬停时仍可写一份主 RUN。“知识库也不要写 / 全局只读 / 任何文件都不要修改 / 本轮不要落盘”禁止本轮知识库写入；“不读知识库 / 不使用知识库”同时禁止读取。

禁止把密码、密钥、账号、客户敏感信息和不必要的完整日志写入知识库。归档与备份默认只读，不静默覆盖或删除。

### 3.1 执行强度只影响编排

任务强度不扩大授权、不降低证据标准、不放宽 Git/MCP/进程门，也不改变“一目标一份主 RUN”。任一更高风险触发优先；会改变分级的关键未知按更高等级处理或只问一个最小问题。

| 等级 | 适用边界 | 默认执行方式 |
|---|---|---|
| S / 小任务 | 目标精确、局部可回退，不涉及共享/公共合同、权限、安全、数据完整性、并发/资源生命周期或外部状态 | 当前页直接完成，做聚焦验证；项目目标结束时仍收口唯一主 RUN |
| M / 普通任务 | 常规功能、缺陷或同根小批量，授权和主流程清楚 | `MVP_FLOW_FIRST`：诊断、最小完整修正、聚焦复验在一个执行轮内完成；普通同根失败最多两轮，只有命中真实风险或用户要求时增加独立审查 |
| H / 高风险任务 | 外部或不可逆操作、数据库/迁移、公共接口/ABI、权限/安全、关键并发/资源、真实硬件、MES、发布、生产、付费、架构边界、外部执行方或已启用六角色接力 | 保留完整合同、独立审查和严格验证；H 本身不新增授权门，只有全局授权规则原本要求单独授权的动作才需当前单独授权；静态或模拟证据不得替代更高层级验收 |

## 4. 真值、未知与身份

不知道就是不知道。有限核查后仍查不到、证据不足或来源冲突时，必须明确标记 UNKNOWN / 无法确认，并记录缺少的证据；不得补造路径、接口、版本、参数、根因、命令结果、工具调用、修改、完成状态、时间、数字、来源或 PASS。

未知会改变行为、范围、权限、数据处理或验收时，向用户提出一个最小问题；低影响未知可保留标记并继续安全工作。历史快照、工具配置和执行者自报都不能自动升级为当前实测事实。

主 RUN 必须区分：

- 执行者：Codex、Kimi、DeepSeek、Qwen、用户或其他实际执行方；
- 软件与页面：例如 Codex Desktop／02·开发；
- 模型：仅在当前可确认时填写，否则写“未知”；
- 角色：总监、诊断、开发、独立审查、修复、验证、外部执行、知识库维护或人工确认；
- 记录者和来源方式：直接执行、直接观察、执行者自报、用户转交、外部报告或人工确认；
- 时间：YYYY-MM-DD HH:mm:ss +08:00；
- 目标 ID 或 MILESTONE_ID：在项目内唯一。

执行者与记录者不同时必须同时保留。开发自检不能写成独立审查通过；审查建议不能写成已修复；局部证据不能升级为更高验证层级。

## 5. 一个目标一份主 RUN

知识库的留痕单位是“完整目标”，不是工具动作或角色消息：

- 非阶段接力：用户当前一个内聚项目目标对应一份主 RUN。
- 阶段接力：一个稳定 MILESTONE_ID 对应一份主 RUN，跨 00–05 角色持续汇总。
- 知识库治理：一项内聚治理目标对应一份治理主 RUN。
- 与项目无关的普通聊天不创建 RUN。

以下内容必须留在同一主 RUN 或角色完成胶囊内，不得另建同义 RUN：任务下发、合同前审、角色派发/回传、状态查询、一次工具/编译/测试失败、普通同根修正、单条审查发现、修复项、复验、阶段判断和硬停消息。

阶段接力由 00·总监 作为主 RUN 维护者。首次派发前创建或核验唯一主 RUN 路径；过程中只允许为准确续页追加 `CONTINUATION_CHECKPOINT`、在回传失败时追加 `RELAY_CALLBACK_FAILED`，或由 00 在可执行合同前审回包后、实现派发前执行一次 `CONTRACT_GATE_UPDATE`：原位更新同一主 RUN 的活动控制块和必要合同正文，并追加一条紧凑 revision 裁决。该例外不得用于粘贴完整回包、记录普通流水、改写无关事实或另建 RUN。其余事实在完成或硬停时统一收口。其他角色通过一次胶囊提供证据，不各写阶段 RUN。若回传和知识库写入都失败，明确报告双重阻断，不声称已同步。

推荐文件名：

RUNS\YYYY-MM\YYYYMMDD-HHmmss_软件-主角色_短目标.md

主 RUN 至少包含：项目、目标/MILESTONE_ID、主维护者、各实际执行者与页面、模型或未知、角色、记录者、时间、授权与范围、输入基线、实际动作、实际修改文件、验证层级与结果、普通修正次数、未知和未执行项、错误/风险、关键 RELAY_ID 与回传状态、影响范围/方案/所有权/兼容/验收/风险的关键裁决（依据、错判代价、重审条件）、结果码、置信度、状态变化和下一关。普通实现细节不建裁决台账。

执行方不能访问知识库时由主维护者代写，并保留“执行者自报/用户转交”等来源。一个主 RUN 内可记录多个角色，但不能把多方证据混成同一执行者或同一验证层级。

## 6. 页面式六角色接力留痕（仅启用时）

本节只定义接力如何进入知识库留痕；角色状态机、合同 revision、回传、防重复、硬停、续页和 20 行胶囊的唯一完整协议是 `{SKILLS_ROOT}\codex-workflow-router\references\kb-stage-relay.md`。

六个固定角色页是职责隔离，不是留痕粒度。文件、命令、测试、一次失败、一条发现和一个修复项都属于当前角色内部微动作；不得因此创建新里程碑或新 RUN。

整个里程碑保持同一 `MILESTONE_ID`、主合同和主 RUN。主 RUN 只记录每个实际 `RELAY_ID` 的目标/返回页、预期与实际角色、活动 revision 链、回传状态、执行者、修改、验证层级、未知和未执行项；胶囊字段按接力协议记录，本文件不维护第二份字段清单。

正常完成与硬停必须走各自唯一目标，过期、重复、错项目、非预期角色或 revision 不匹配不得推进。角色不另建阶段 RUN；总监在完成或硬停时一次性整合主 RUN和核心状态。同角色续页只在同一主 RUN 写 `CONTINUATION_CHECKPOINT` 并完成语义回读，不创建新里程碑、阶段 RELAY 或 RUN。

## 7. 两层写回

第一层：一个完整目标或里程碑维护一份主 RUN。

第二层：仅在事实或状态真实变化时，由主维护者在目标完成或硬停时一次性同步：

- 当前状态 → STATUS.md；
- 待办或阻断 → TODO.md；
- 风险 → RISKS.md；
- 有证据的完成项 → DONE.md；
- 当前入口、禁区或下一关 → START_HERE.md；
- 稳定问答 → FAQ.md；
- 可复用踩坑 → LESSONS.md；
- 重要阶段或结构变化 → CHANGELOG.md。

核心文件只保存状态差量和主 RUN 引用，不复制角色胶囊或完整日志。并行执行者不同时写同一核心文件；主维护者负责整合，避免覆盖和口径冲突。

## 8. 事实状态、冲突与验证

新增事实记录来源、时间、依据和置信状态：

- 已确认：有当前可靠证据或用户明确确认；
- 需确认：来源或当前适用性不足；
- 静态推测：仅由静态文件推断；
- 需实测：需要构建、运行、GUI、DLL、硬件、MES 或生产验证；
- 需人工确认：需要负责人或业务方裁决；
- 冲突待人工确认：当前证据无法裁决多个来源。

用户当前更正优先，但旧结论不静默删除；在主 RUN 中保留来源并追加更正。静态、构建、Debug/Release、自动化、运行、GUI、DLL、NoHardware/模拟、硬件、MES、安全和生产证据必须分别记录，不能互相替代。

## 9. 踩坑、限长与归档

普通失败先记录在当前主 RUN；只有可复现、成本较高、可能再次发生且已有足够根因证据时，才去重提炼到 LESSONS.md。未知根因不得伪造成稳定经验。跨项目稳定适用后再提升到治理或 02_Knowledge。

写核心文件前检查职责和大小：

- START_HERE.md 目标约 500–1500 中文字且不超过 8 KB；超过 12 KB 禁止继续追加历史。
- RULES.md 目标不超过 16 KB；超过 20 KB 停止追加并先归档压缩。
- STATUS.md、TODO.md、RISKS.md 只保留当前项，历史转主 RUN 或归档。
- RUN、LESSONS 和归档不作为每次启动的默认全文。

优化必须可恢复：先完整归档原文件并标明时间、来源和原因，再精简；不得静默删除历史。

## 10. 新项目与收口

新项目只有用户明确同意后才能创建于 01_Projects\【项目名】。最小模板只写项目名、来源、背景、已确认事实、待确认、允许和禁止；不得臆造路径、架构、硬件、接口、测试或发布状态。

完整目标结束时：

1. 创建或收口唯一主 RUN；
2. 核对执行者、来源、实际修改、验证层级、未知和未执行项；
3. 只同步一次真实核心状态差量；
4. 判断是否有已证实且可复用的 LESSON；
5. 检查 START_HERE.md 与 RULES.md 限长；
6. 使用非 Git 方法核对实际写入文件；
7. 向用户报告结论、实际修改、验证、未知/阻断和下一关。

不得为了证明工作量重复写入相同结论。
