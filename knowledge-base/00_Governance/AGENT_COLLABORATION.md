# 原生父子子智能体协作

本文件把知识库的单目标留痕规则与原生子智能体协调方式接起来。它不创建额外授权，也不替代全局规则、项目合同或当前运行时限制。

## 1. 任务所有权

主任务持有用户目标、范围、授权、合同和唯一主 RUN。子智能体只完成直接父级分配的一份内聚工作包，并把证据回给父级；父级核验、整合并统一收口。普通派发不创建或切换用户任务页。

一个内聚目标或里程碑保持一份主 RUN。派发、回包、工具失败、发现、修复和复验都归入同一份记录；不要按角色或命令另建同义 RUN。普通聊天不创建 RUN。

## 2. 派发合同

每份派单应有唯一 DISPATCH_ID，并说明目标、必要输入证据、精确范围、允许和禁止的操作、依赖、完成条件、修正预算以及直接父级回包对象。派单边界不清时先在主任务内补齐，不让子智能体猜权限。

至少两个必要工作包边界清楚、互不阻塞且预期缩短总耗时时，优先同批并行；小且共用验证面的工作由同一执行者完成。写同一文件、浏览器标签或共享状态时指定唯一写入者并串行执行；需要独立审查时，审查者不能承担被审查对象的修改。

## 3. 有限协作树

一套可选的专业层级是：

- 主任务统一分配 01·诊断、02·开发、03·审查、04·修复或 05·验证角色。
- 01—05 可在父级允许且运行时支持时，派发专项叶节点：doc-writer、fe-designer、image-analyst、log-forensics、mini-coder、night-guard、run-trace-auditor、spc-data-analyst、wpf-designer、x-topic-scout。
- 专项叶节点不得继续派生；01—05 不彼此派发，不用 default/worker/explorer/luna_worker 或新建用户页面绕过白名单。每个专业角色在原生模式也加载其唯一主 Skill，由父级承担下一角色调度。
- 本参考工作流的全树执行上限为 8 个，不含主任务；当前运行时或合同更低时服从较低限制。由主任务分配全部名额，不能把分支上限当作全树上限。

子级只继承父级已获授权的能力，不因角色名称、工具可用或独立任务记录而获得额外权限。用户级审批仍由用户授权，子智能体不能相互转授。

## 4. 事件与回包

使用实际可用的原生协作工具派发和收取结果。对每个派单只发送一次；不轮询、广播或让用户手动转发。任务正在运行时使用事件回包或有界阻塞等待，在运行时允许范围内采用较长等待并复用游标；无变化超时直接续等，不叠加时钟、历史查询、催办或空进度。不能把“已派发”写成“已完成”。

直接父级收到一次简洁回包，至少包含：

- DISPATCH_ID 与实际承担角色；
- 结论及准确证据位置；
- 实际修改和实际验证层级；没有修改或验证时明确写出；
- 未知、未完成、失败和下一步；
- 若启动了后台进程，说明进程身份与清理状态；未启动则写 NONE / NOT_NEEDED。

子智能体的自报是输入证据，不自动等于独立审查、独立验收或最终 PASS。

## 5. 权限和证据边界

Git、外部发布或发送、付费、真实数据写入、真实硬件、生产操作和重要资产删除，按全局规则取得当前所需授权。子智能体不扩大或代替授权。

模型、推理强度、服务层和技能配置只是预设。专业角色固定 default；缺少服务层遥测且没有相反证据时可继续并写 SERVICE_TIER_ACTUAL=UNKNOWN，不能声称非 Fast 已实测。明确冲突或固定角色不可用时回报 SUBAGENT_TIER_BLOCKED，不静默换模型或回退 Fast。静态检查、模拟、Debug 或单测结果只报告相应验证层级，不扩大成 GUI、Release、真实设备或生产 PASS。
