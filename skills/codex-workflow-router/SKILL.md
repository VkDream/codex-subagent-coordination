# Codex Workflow Router

Use this skill as a front-door router for multi-capability work. Its default route is direct native-agent interaction: the current task dispatches a bounded specialist and receives one verified callback. It chooses a small, explainable set of Skills, MCP tools, models, and subagents; it does not replace project instructions, user authorization, or a specialist Skill's workflow. Page-based stage relay is opt-in only when the user explicitly requests it.

## When to use

Use it when the user:

- asks which Skill, MCP, plugin, or tool should be used;
- asks to discover, compare, organize, install, or create Skills;
- combines research, local files, code, browser state, external services, and artifact creation;
- asks whether an MCP or package is current, compatible, or safe to use;
- wants a smoother workflow with fewer repeated instructions or lower context cost.
- wants evidence, design, or context-compression quality gates added to an existing workflow;
- asks to initialize the current saved Codex project and start knowledge-base stage relay;
- asks Codex to continue one project through director/planning, diagnosis, development, independent review, remediation, or GUI validation in separate low-context tasks.

Do not load this router for a clear single-domain request when one specialist Skill is an obvious fit.

## Routing method

1. Identify the outcome first: answer, research, source change, review, artifact, browser interaction, external-system action, or Skill/MCP maintenance.
2. Prefer an established personal, bundled, or installed plugin Skill that already matches the outcome. A downloaded candidate is reference material until runtime discovery is separately confirmed.
3. For the user's recurring workflows or an ambiguous cross-domain request, read `references/personal-skill-map.md`. Treat each category as an index, never as a bundle to load.
4. Choose one primary Skill. Add at most one supporting Skill when it contributes a distinct required phase; add a second only for another independent and indispensable phase. Do not load a whole category because its name sounds relevant.
5. For project, engineering, technical research, external-system, or current-evidence work, apply the global `MCP_GATE` before falling back to shell, `rg`, direct file reads, or ordinary web browsing. Routing-metadata checks such as exact CWD, path, project identity, index presence, or configured server names may precede the probe. Choose the narrowest useful route:
   - current OpenAI, Codex, ChatGPT, or OpenAI API facts: use OpenAI Developers Docs MCP; if unavailable, use the `openai-docs` Skill with official OpenAI web sources. Do not route official OpenAI facts to Context7;
   - current third-party library or API documentation: use Context7 after resolving the library ID. For an existing project, first identify the relevant dependency version from current project evidence and query matching documentation; distinguish a declared range from a resolved or installed version. If the version is unknown, matching Context7 docs are unavailable, or sources conflict, state the gap and consult official documentation without silently substituting the latest version. For questions without a project, follow the user's requested version or scope. Looking up documentation does not authorize dependency upgrades;
   - indexed cross-file structure, dependencies, or call graph: use CodeGraph; without an index or loaded CodeGraph tool, use the narrowest `rg` and current-source reads;
   - GitHub repository, issue, pull request, release, or commit evidence: use local `mcp__github__` first; use the GitHub Connector only when the local route is unavailable or lacks the needed authorized capability. Do not fetch the same evidence through both routes without a stated reconciliation need;
   - public web evidence: use web search; signed-in Chrome state: use Chrome control; in-app browser state: use in-app browser control; isolated local web testing: use Playwright; native Windows application state: use computer-use;
   - data-analysis artifacts: use the Data Analytics MCP for supported requested outputs;
   - local JavaScript or browser-support work: use a bounded Node REPL;
   - exact-file, exact-symbol, or exact-line inspection may use direct reads only when that is strictly narrower and no cross-file relation or current external fact is required; record `DIRECT_READ_NARROWER:<target>`;
   - use no MCP only with one explicit allowed reason: `NO_RELEVANT_MCP`, `MCP_UNAVAILABLE:<server>`, `DIRECT_READ_NARROWER:<target>`, or `MCP_NOT_USEFUL:<server/tool>` after one bounded probe establishes the limitation.
6. Apply authorization before execution. A read-only route does not authorize writes. Do not install a public Skill, call a write-capable MCP tool, alter external data, touch hardware/MES/production, or invoke Git merely because the route suggests it.
7. For a version or “latest” request, separate these facts: configured version expression, published/latest version, resolved or installed version, actually running version, and compatibility. If one is unknown, report it as unknown instead of inferring it from `@latest`.
8. Load `references/capability-map.md` only when the complete local inventory or MCP snapshot is required. Load `references/online-skill-sources.md` only when evaluating public Skills. Do not load either for an obvious single-domain task.
9. When the user explicitly initializes the current saved project with stage relay (including the shorthand `创建当前新项目并开启阶段接力`), enables automatic task switching, or says to enter the next project stage while relay is already active, read `references/kb-stage-relay.md`. Do not load it for an ordinary single-task handoff, and do not create a new task without that explicit relay request.
10. When the request or current milestone explicitly benefits from stronger evidence traceability, UI/design discipline, or large-output context reduction, read only the applicable section of `references/quality-gates.md`. Keep every gate `OFF` unless it changes a real decision or acceptance check. These gates supplement the chosen domain Skill; they never become a second orchestrator, memory system, execution authority, or evidence-level upgrade.

## Cost-aware orchestration

- Use the simplest, fastest viable fix with the smallest sufficient change. Once the actual entry point and cause are clear, implement within existing authority, run the smallest meaningful verification, and deliver the complete outcome. Do not turn ordinary failures into extra tasks, approvals, repeated reads, or formal review rounds. Reuse valid evidence; stop only the affected action at a real permission, data-safety, contract, or exhausted-budget boundary. Preserve actual tool capabilities and user-selected settings. Start with the current agent and the narrowest relevant callable tool; use a Skill only when it changes the work usefully. Follow the existing MCP and authority rules without adding ceremonial probes or repeated loading.
- If the route starts a background or long-lived process, apply the global process-ownership gate; this router never owns or cleans a host MCP process.
- Prefer parallel dispatch when at least two independent work packages can reduce elapsed time, including multiple instances of the same named role. Keep writes disjoint, shared resources isolated and dependent work ordered; combine small tasks sharing one verification surface. Follow the global `AGENTS.md` for the whole-tree ceiling and budget allocation; a lower current contract or runtime limit still applies. Do not fill spare capacity with artificial tasks. Model, reasoning, service-tier, Fast restrictions, pinned-role selection, and fallback behavior remain owned by the global `AGENTS.md`; this router only selects an allowed route and records the actual result. Keep the professional role preset at `service_tier=default`. When runtime tier telemetry is absent, it is `SERVICE_TIER_ACTUAL=UNKNOWN` and does not alone stop an otherwise valid dispatch; never claim non-Fast was verified. Stop the affected route and record `SUBAGENT_TIER_BLOCKED` if observed runtime settings contradict the requested model/effort/default tier, or the fixed role is unavailable or rejected. Never silently switch models or enable Fast.
- Follow the delegation depth and specialist allowlist in the current global `AGENTS.md`. Its authorized native-role exception permits parent → 01–05 → specialist only; 01–05 must not spawn one another, and specialist leaves cannot delegate. Keep the global concurrency budget across the whole tree, preserve the dispatching role’s permissions, and return each specialist result to its immediate parent for verification. Other agents remain one level deep. Send only task-relevant context and do not leave assigned work in flight after reporting completion.
- Reduce context at the source before adding a compression layer: use exact source roots and exclude applicable generated/dependency directories with globs that match nested paths (for example `!**/wwwroot/assets/**`); inspect artifacts explicitly when they are the subject. Follow the global combined-result exploration budget, set supported output limits before calling, and filter structured replies before printing. Select relevant original text and source once, without duplicate highlights or summaries. Parse long single-line records before selecting fields and avoid rereading valid evidence. After an oversized or truncated result, narrow or paginate the next call instead of repeating it. Do not treat running status or repeated compaction without new evidence as useful progress. Treat external compression packages as candidates until an isolated simulation preserves all critical markers on representative data. Do not enable a proxy, wrapper, MCP registration, persistent memory, or learning/writer feature without current explicit authorization.
- Coordinate through event replies or bounded waits: combine relevant targets where supported, reuse cursors, and use a longer wait within the current runtime limit. An unchanged timeout leads directly to another bounded wait, not a chain of clock/status/history queries, reminders, or repeated narration; preserve communication required by the runtime. Investigate only new evidence, blockers, user input, or an agreed checkpoint. Do not claim that model wakeups are token-free or create pages, background polling, or automations to bypass waiting limits.
- Batch small, independent, same-shape work that shares one verification surface into one subagent dispatch. Do not create one child per file, finding, test, or mechanical edit; keep work separate when meaningful independent delivery, different judgment, state ownership, permissions, or independent evidence justify parallel work.
- For a native agent context handoff, require the old agent to return a checkpoint and stop writing, then let its parent spawn a fresh instance of the same role with minimal context (`fork_turns=none` when supported), a new DISPATCH_ID and CONTINUES_DISPATCH_ID. Preserve the same contract, evidence, permissions and cumulative budget; reject late superseded callbacks. Do not create user pages or claim deletion/slot release without a supporting lifecycle tool.
- Hand off exact file pointers, stable contract identifiers, and compact evidence capsules instead of repeatedly pasting plans, logs, or diffs into prompts. A reviewer may reuse current, legible evidence while independently judging its relevance; rerun only when evidence is stale, missing, contradictory, affected by later changes, or the requested evidence level requires a fresh independent run.
- For enabled knowledge-base stage relay, read and execute `references/kb-stage-relay.md` instead of restating its state machine here. The router only enforces its entry conditions: the relay is user-owned rather than a subagent, uses one user-valued milestone and one master RUN, loads only the current fixed role's `kb-role-*` Skill, and keeps `03·审查` independent. Ordinary native-agent interaction does not load this relay protocol or create/switch role pages.
- Page relay dispatch remains event-driven when explicitly enabled: after one exact dispatch stop; never poll or broadcast. Roles decide between finishing within their own remit, a direct handoff to one contract-authorized specialist, and a real director decision. Normal completion selects one approved result branch; hard stops only return to the director. Carry the shared retry budget across roles and do not notify the director of routine progress; stale/duplicate/unexpected callbacks cannot advance state. Authorized page replacement follows reference §10 only for that explicit page mode. In native-agent mode, return the bounded result to the immediate parent and do not create, switch, reread, or register user pages. Do not repeat confirmation already given by the user.

## MCP evidence

Use the global MCP routing and failure policy without repeating the same checks. A failed or unavailable route does not stop other authorized work: switch to the narrowest permitted fallback and report the limitation. Configured or listed tools are not proof of actual use.

## Route record

Keep only the useful route decision and actual evidence. For technical/project delivery and relay callbacks retain MCP_ROUTE, MCP_EVIDENCE and MCP_FALLBACK as required by global rules. Include PROCESS_OWNERSHIP and PROCESS_CLEANUP when applicable; relay callbacks keep their required schema. No separate full routing form, gate table or empty-field report is needed for ordinary work.
