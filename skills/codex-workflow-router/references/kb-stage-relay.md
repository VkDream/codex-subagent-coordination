# Knowledge-Base Stage Relay V3.7

仅在用户已为一个精确保存项目开启知识库阶段接力、要求自动路由，或当前固定角色需要继续当前里程碑时读取。该协议管理 Codex 任务页和紧凑回传，不配置 DSH、MCP、模型默认值、Git、工程权限或外部系统。

## 1. 权限与项目身份

- 接力只授权在已确认的保存项目 ID 和精确路径中查找、首次创建、命名、复用和消息连接六个固定角色页，并按知识库规则维护一个里程碑主 RUN。
- 接力本身不授权工程修改、构建、运行、GUI、外部写入、Git、数据库、硬件、MES、发布或生产。工程权限必须来自用户当前合同。
- 项目 ID、路径或活动角色不唯一时停止并提出一个最小问题，绝不从相似标题或历史路径猜测。
- 用户禁止知识库写入时，不声称已建立可持久接力；只给 20 行内手工胶囊并停止。

## 2. 初始化当前项目

口令“创建当前新项目并开启阶段接力”只授权：确认当前保存项目和路径、创建最小知识库项目、创建一份初始化主 RUN、将当前页设置为 00·总监 并启用接力。它不授权工程或外部操作。

1. 必须确认唯一保存项目 ID 和精确本地路径。
2. 将当前页标题直接设置为字面量 00·总监，读取一次任务元数据并核对严格相等；不相等时返回 RELAY_TITLE_MISMATCH，最多纠正一次。
3. 只创建已确认事实，不臆造里程碑、架构、接口、路径或验证。
4. 现有代码只有确需当前技术基线时才首次创建 01·诊断；空项目留在总监讨论路线图。
5. 不创建“立项·建档”“R000·规划”或六个空白角色页。

## 3. 六个固定角色与 Skill

每个项目只维护以下活动角色页，进入后必须加载且只加载对应主 Skill：

| 活动标题 | 主 Skill | 完整职责 |
|---|---|---|
| 00·总监 | kb-role-director | 一份路线图、一个完整里程碑合同、阶段决定、主 RUN 与最终收口；不改工程、不自审 |
| 01·诊断 | kb-role-diagnosis | 一次交付完整基线或根因包；默认只读 |
| 02·开发 | kb-role-development | 一次完成完整实现、普通同根修正、聚焦验证和自检 |
| 03·审查 | kb-role-review | 独立只读地审完整诊断、合同或实现，区分三种模式并汇总全部高置信发现 |
| 04·修复 | kb-role-remediation | 一次批量修复同合同内已验证发现，聚焦复验后回独立审查 |
| 05·验证 | kb-role-validation | 一次完成合同指定层级的独立验收，不改工程 |

活动标题必须逐字等于表中名称，不加项目、模型、里程碑或命令。其他角色页首次真正需要时才创建，之后复用。六个标题是职责槽位，不要求六页始终同时存在。

模型、推理强度、service tier、Fast/Sol 和子智能体默认值只由全局 `{GLOBAL_AGENTS}` 规范，本接力协议不另设默认值。已授权创建角色新页时，核对当前用户对目标页确认的模型与推理设置，显式向 `create_thread` 传入 `model`、`thinking`；没有可确认设置时先补齐，不从原生子智能体 TOML、发送方或旧页猜填。复用现有页的普通派发/回包保持原设置，不附带模型覆盖；子智能体不套用角色页模型表。派发胶囊记录期望值，完成胶囊只记录运行态可确认的实际值；无法确认时写 `unknown`，不得把期望值或配置值冒充已生效。

## 4. 工作粒度

### 里程碑

一个完整、内聚、用户可感知、可一次验收的业务流、功能、缺陷族或阶段结果。全程保持同一 MILESTONE_ID、主合同和主 RUN。

### 角色阶段

同一里程碑中的一次角色激活。角色完成后只发一个证据胶囊，不创建自己的 RUN。

### 微动作

文件读取/修改、命令、构建、测试、一个失败、一条发现、一个修复项或一次复验。微动作全部留在当前角色内，不得创建任务、合同、接力、里程碑或 RUN。一次角色激活应覆盖该角色职责内的完整工作包，在原授权和预算内连续完成必要核查、实现、自检、普通修正与聚焦复验，再统一回传；内部列步骤或分组不等于新派发，不要求用户逐步确认。

不要把“大轮次”误解成无限范围。一个里程碑应能由同一合同、同一权限边界和同一验收矩阵闭环；若用户价值、权限、依赖或验收实质不同，再拆为下一个里程碑。

00·总监在形成合同时将过程深度标为 `PROBE`、`BOUNDED` 或 `ARCHITECTURAL`：分别对应可行性/假设验证、现有清晰流程的边界改动、以及实质改变系统边界或关键质量属性的架构工作。分类不新增角色、RUN 或审批；隐藏复杂度只能升级并回总监重裁，不能为了省流程降级。

## 5. 角色自主判断与直接接力

每页依次判断：职责内且权限/预算允许的工作在本页闭环；本阶段完成或明确需要另一专业角色时，按合同允许分支直接交接；只有目标/范围/权限/验收改变、真实接单冲突、不可替代条件缺失或无进展且预算耗尽时升级 00。职责独立不等于每一步都经总监转发。

默认路径：00 定目标与边界 → [01 诊断 → 03 DIAGNOSIS_REVIEW] → 已获准的 02 或 04 → 03 IMPLEMENTATION_REVIEW → [05 必要验收] → 00 收口。需要首次批准、实质合同变更或强制前审时，03 CONTRACT_REVIEW → 00 放行；已有有效批准不因补诊、返修或转页重复前审。

- 01 整包交付根因、证据、最小方案和验证建议，正常直达 03，不让 00 只做转发。03 的 DIAGNOSIS_REVIEW 只评诊断/方案，不能伪造实现审查或合同批准；可自行补齐的小缺口当页查明，需专业补诊时整包退 01。
- 03 诊断评审通过后，若当前合同已批准该范围和执行角色，直接交预定 02/04；否则带具体待批准事项回 00。高风险/外部执行的强制前审不跳过。
- 02/04 完成修改、自检、同根普通修正和聚焦复验再交 03。编译/路径/夹具错误不是自动退单理由。03 一次审完整包，修复后只查已改及受影响部分；05 保存失败证据后继续安全且不依赖该失败的检查，再集中回包。
- 03/05 发现已授权范围内的明确缺陷直接交 04；需补诊且合同允许则交 01。整包修复后仍经 03；05 不承担源码修改，03 保持只读。
- 05 仅在合同确需独立实际验收时进入；无需更高层级时 03 交 00 收口。总监核对最终用户行为和证据，不重做角色已完成的检查。

### 跨页防循环与计数

合同预设同一问题包的跨页退回预算，默认最多 2 次；补诊和返修共用，不能各自重新获得 2 次。路由到 01（补诊），以及 03 实现审查/05 → 04（返修）各消耗一次；首次诊断评审通过后进入已批准的实施角色不算退回。一个完整退回覆盖整包，不逐条回传。累计值随交接保留，换页、换角色、换 RELAY_ID/revision 不清零，独立问题不得偷偷混入同包。

页内普通修正的 FIX_CYCLES 按“基于一次结果作出的集中纠正并复验”计数，不按文件、编辑、命令或字段补正计数；默认最多两轮，合同已有更严格真实风险上限继续遵守。跨页预算与页内预算分别说明，已耗尽的页内修正不能靠转页续命。

一次失败不立即停；同一失败经完整纠正仍无新证据、无方案变化时，不原样再试。预算耗尽且仍未解决回 00，说明改变方案或解除条件的具体需求；只追加计数上限不是有效裁决。已通过且未受改动影响的检查不重复。

- 用户指定 DSH、DeepSeek、Kimi 或其他外部执行方时，只有当前 revision 已完成 03 独立前审并由 00 放行后才生成或发送一个 `EXECUTOR_KIND=EXTERNAL` 的完整外部合同；外部合同必须为 `PRE_REVIEW_REQUIRED=YES`、`PRE_REVIEW_RESULT=APPROVED` 且携带真实 `APPROVED_RELAY_ID`，不得继承内部 BOUNDED 路线的 `NO/NOT_REQUIRED` 跳过组合。这里“真实”表示 00 能在同一 `MASTER_RUN` 的活动控制块或 `CONTRACT_GATE_UPDATE` 中定位到同一 `PROJECT_ID`、`MILESTONE_ID`、`CONTRACT_REVISION`、`ROLE=03·审查`、返回 00 的 `CALLBACK_TARGET_THREAD_ID` 且 `APPROVAL_STATUS=APPROVED_ACTIVE` 的前审回包，并且 `APPROVAL_UPDATE_ID` 精确指向该主 RUN 当前唯一有效的 `CONTRACT_GATE_UPDATE`；缺失、过期、重复、错主 RUN/更新/项目/里程碑/revision/角色/回传目标均不得派发。外部执行方正常完成先回 00，由 00 核对 `CONTRACT_REVISION_EXECUTED` 后再派 03 做 `IMPLEMENTATION_REVIEW`，不重复派内部开发/修复。

## 6. 里程碑合同

00·总监为每个里程碑定义：

- MILESTONE_ID、用户价值目标、完成定义；
- PROCESS_DEPTH（`PROBE/BOUNDED/ARCHITECTURAL`）及升级条件；
- 保存项目 ID、工程路径、当前事实和显式 UNKNOWN；
- 允许、禁止、授权来源、改动边界；
- 交付物、验收矩阵、验证预算和不代表的层级；
- 依赖、自动修正预算、修复复审次数；
- MASTER_RUN 精确路径；
- 预期角色路径、当前活动角色 ID、按结果选择的允许分支、跨页退回累计/上限和真正硬停条件；只登记本任务可能需要的角色，不为填表创建页面。
- 影响范围、方案、所有权、兼容、验收或风险的关键 `RULING`；每条包含依据、错判代价和重审条件，普通实现细节不记录。

合同在整个里程碑内稳定。只有目标、范围、权限、依赖、数据处理或验收实质变化时回 00 变更合同；技术 RELAY_ID 的变化不构成新合同。

## 7. 事件驱动回传

每次跨页派发都包含：

- 同一 MILESTONE_ID；
- 唯一 RELAY_ID；
- 精确 TARGET_THREAD_ID、固定返回页 RETURN_TO_THREAD_ID 或已批准的结果分支 routing，以及始终指向 `00·总监` 的 HARD_STOP_RETURN_TO_THREAD_ID；
- 当前角色、各分支预期接收角色、选择依据及唯一下一动作；分支目的页和任务范围必须来自当前合同，不能临时猜页或扩权；
- MASTER_RUN 路径、当前修复复审计数和完整权限边界。
- 可执行合同派发还包含与实际接收方一致的 `EXECUTOR_KIND=INTERNAL_02|INTERNAL_04|EXTERNAL`、`CONTRACT_REVISION`、`CONTRACT_STATE`、`PRE_REVIEW_REQUIRED/RESULT`、`APPROVED_REVISION/RELAY_ID`、`APPROVAL_UPDATE_ID`、`APPROVAL_STATUS` 和 `DEVELOPMENT_ALLOWED`；执行方不能只收到一个其可能无法访问的主 RUN 路径。00 在外部派发前必须完成上述批准绑定核对，执行方仍需检查胶囊字段完整且 revision 一致。外部执行方看到 `EXECUTOR_KIND` 缺失/不符、批准字段缺失/不一致或任何 `NO/NOT_REQUIRED` 跳过组合时，必须在工程动作前以 `CONTRACT_INTAKE_REJECTED` 硬停回 00。

发送前由当前角色根据真实结果选择一个允许分支，按共享适配器生成唯一目标；未启用分支的在途派发仍按原 RETURN_TO_THREAD_ID，不私改绑定。只发送一次，成功后立即结束，不等待、不监工、不抄送总监。硬停始终只发给 HARD_STOP_RETURN_TO_THREAD_ID。胶囊写明 PRIMARY_SKILL、CALLBACK_KIND、实际 CALLBACK_TARGET_THREAD_ID；使用分支时还保留 CALLBACK_TARGET_ROLE 和 RELAY_RETRIES_USED。

直接交接必须包含任务的精确证据入口、为何转交、对方要完成什么和完成条件，放在 FINDINGS_OR_RESOLUTION / RECOMMENDED_NEXT_GATE；沿用同一合同与主 RUN，不重新粘贴历史。接收方核对真实来源、当前活动角色与 revision，先消费该回包一次，再从既有合同建立本阶段唯一 RELAY_ID 和发送前 context；保留来源 RELAY_ID、执行来源、全部适用批准链及累计预算。职责/授权未变不需 00 再派一次。不具备可靠的活动角色或消费状态就回已确认的 00 解决实际缺口，不猜填。正常阶段进度只随证据传递，00 不接收流水通知。

发送前执行共享适配器 `{SKILLS_ROOT}\codex-workflow-router\references\relay-callback.md`：用原派发/活动合同作为独立 context，生成并校验最终 `{threadId,prompt}`，然后原样发送一次，不手拼另一份回包。字段笔误在本角色内补正，不增加业务修复轮次或重跑已执行工作；真实身份/来源/批准/revision 冲突仍硬停。硬停允许携带缺失/冲突的上游信息，只向已确认的 00 告警。适配器不替代接单、批准台账、去重或发送回执门，旧格式在途包按适配器兼容段处理。

可执行合同的来源与 revision 必须沿实际路径被下游消费并向终点传播：02、04 和外部工程执行方回与真实来源一致的 `EXECUTOR_KIND_ACTUAL` 及 `CONTRACT_REVISION_EXECUTED`；03 实现审查先核对来源分类，外部来源还核对强制前审，再回 `CONTRACT_REVISION_REVIEWED` 并保留已核对的执行方分类与 `EXECUTED`；05 保留执行链并新增 `CONTRACT_REVISION_VALIDATED`。03/04/05 在实际审查、修改或验收前必须将适用的上游字段与活动合同比较；缺失、`UNKNOWN` 或不一致时只硬停回 00，不走普通发现、修复或验收路线。

角色若启动过后台或长驻进程，必须在完成或硬停回传前按全局进程所有权门处理精确会话/进程树，并在胶囊中写明 `PROCESS_OWNERSHIP`、`PROCESS_CLEANUP`；未启动则写 `NONE/NOT_NEEDED`。不得为清理而扫描或终止用户后台、其他角色页或 Codex/MCP 宿主进程。

禁止：

- wait_threads 使用正超时；
- 循环 read_thread、list_threads 或状态轮询；
- 固定间隔唤醒、心跳消息或同一阶段重复派发；
- 一个角色自行创建孙任务或向多个页面广播；
- 把“回总监/回审查”文字当成已经执行的消息。

只有用户明确问“检查接力状态”时，才允许一次 timeoutMs: 0 的即时快照，返回后结束。

## 8. 未知与硬停

角色先在授权范围内做有限核查。仍查不到或证据冲突时明确 UNKNOWN / 无法确认，不能补造路径、接口、版本、根因、执行、修改或 PASS。

UNKNOWN 先在当前角色授权与剩余预算内做定向核查；可自行查明或属于已授权实现细节时页内解决，不因标记 UNKNOWN 就立即回传。有限核查后仍缺少不可替代证据，或继续会越过行为、范围、权限、数据处理或验收的实质边界时，停止相关操作并向总监一次回传证据、阻断和恢复条件；其余不受影响的安全工作可先完成，但不得绕过接单/批准门或明确停止条件。总监先在既有授权内裁决，只有不可替代的用户输入、选择或新授权才提出最小用户问题；低影响 UNKNOWN 可保留后继续。严格停止条件的设定与同一阻断重派遵循全局“审查与验证”，执行方不得自行放宽生效合同。

硬停不是丢包：必须只向合同中精确指向 00·总监 的 HARD_STOP_RETURN_TO_THREAD_ID 回传一次，包含已完成的安全工作、实际修改、验证、未知/阻断、未执行项、当前工程状态和建议下一关。不得同时向正常返回页发送，不得让用户手动转发，不得自动扩大权限或在预算外重跑。

回传失败时：

1. 不做近似参数盲重试，不使用计算机控制绕过；
2. 若知识库允许写入，只向既定 MASTER_RUN 追加一段 RELAY_CALLBACK_FAILED 胶囊，不创建新 RUN；
3. 若知识库也写入失败，当前页报告双重阻断并保留可复制胶囊；
4. 不声称总监已经收到。

接收方在推进前核对项目、MILESTONE_ID、来源 RELAY_ID、预期角色、分支累计预算、当前待处理状态，以及本路径适用的 `CONTRACT_REVISION_EXECUTED/REVIEWED/VALIDATED`。过期、重复、错项目、非预期回传或 revision 不匹配只拒绝并记录；一个有效回传最多触发一个下一阶段。

## 9. 一份主 RUN

里程碑首次派发前由 00 创建或核验一个 MASTER_RUN；整个 00–05 流程只维护该文件。过程中只允许由创建方在新页就绪后为本次换页更新一条活动页映射、为总监或未完成任务续页追加必要 `CONTINUATION_CHECKPOINT`、在回传失败时追加 `RELAY_CALLBACK_FAILED`，或由 00 在合同前审回包后、实现派发前执行一次 `CONTRACT_GATE_UPDATE`：原位更新活动控制块和必要合同正文，并追加一条紧凑 revision 裁决。不得借此粘贴完整回包、记录普通流水或另建 RUN。普通派发、回传、失败、发现、修复和复验不追加流水。普通角色胶囊不是 RUN。总监在完成或硬停时统一汇总：

- 各角色实际执行者、页面、模型或未知、时间和来源；
- 实际修改文件与最终状态；
- 已执行验证及精确层级；
- 所有高置信发现、已接受/拒绝修复、修正次数；
- 当前批准 revision 的有效链中，02/04/外部执行、03 审查和实际进入的 05 验证所回传的 revision 是否全部等于最终 `APPROVED_REVISION`；未进入的阶段不造字段，已作废 revision 的历史回包不参与当前等值判断；
- UNKNOWN、未执行、风险、关键 RELAY_ID 和回传状态；
- 最终结果码、置信度和下一关。

核心 STATUS/TODO/RISKS/DONE/START_HERE 也只在里程碑完成或硬停时由总监同步真实差量。派发、回传、状态查询、一次失败、单条发现和复验不创建 RUN。

## 10. 换页按角色与当前任务分流 V4

页面流程约定：总监换页才需要完整上下文交接；01–05 空闲换页直接创建新页、加载对应 Skill 并待命。先判断以下三种情况，不把所有换页都套成总监交接。当前用户明确换页就是本次创建授权，不重复询问；模型/推理默认表本身不授权换页。

| 当前情况 | 换页方式 | 新页完成条件 |
|---|---|---|
| 00·总监 | 按 §10.3 同步目标、决策、进度和在途绑定 | 必要旧页回读与简短 ACK 一致，执行唯一下一动作或等待 |
| 01–05 已完成/空闲，且无未完成任务、在途执行或待处理回包 | 按 §10.1 直接创建，只加载本角色 Skill | 一句就绪，等待明确新任务 |
| 01–05 仍有未完成任务或在途工作 | 按 §10.2 留简短进度说明后续作 | 保留实际进度、权限、预算与回包绑定，不重复执行 |

分类优先复用当前已知状态和现有登记；不足时只查精确任务状态或在途字段。UI idle 不单独证明任务已结束；状态未知时先保留未完成项、补齐所缺事实，不擅自按空闲覆盖。不得为了确认待命而唤醒所有旧页、扫描历史或开展交接审查。

### 10.1 01–05 空闲换页：直接创建并就绪

1. 由当前已获授权的创建方一次核对项目 ID、CWD、角色、旧活动页和模型表。批量换页由同一创建方完成，不向五个旧页分别发送“准备交接/自行创建”的任务。保留现有全局/项目规则，不为换页降低模型或推理强度。
2. 按精确保存项目在原目录创建每个新页一次，显式传入本角色 model/thinking 和逐字固定标题；遵循用户指定的环境，本次换页不自动建立 worktree 或调用 Git。初始提示只包含项目 ID、CWD、角色、对应 Skill 路径，以及“仅加载该 Skill，回复就绪后等待新任务，工程动作=0”。
3. 新页加载自己唯一的角色 SKILL.md 即止步；当前已提供的全局/项目约束继续生效，确有缺失的适用规则才定向补读。不得为待命完整重读已提供规则、加载接力全文、合同、主 RUN、旧聊天或历史证据；不进入 Skill 后续的工程接单、诊断、审查、验证或回传。新任务真正到达后再按角色读取该任务的合同、当前项目入口和必要证据。
4. 创建方用真实创建回执取得新 ID，此时只记为已创建，保持原活动页映射。必须从精确新页的简短结果确认对应 Skill 已加载成功，才可核对活动登记原值仍为精确旧 ID 并一次切换到新 ID；创建回执不能代替就绪结果。需要等待时做一次有界批量等待，逐页区分已就绪、仍运行、失败或未知；批量等待只返回部分结果时，只登记已就绪的页，其余保留已创建/待确认，不宣称整批就绪、不发催报消息或循环轮询。批量共享写串行完成，已有锁则复用，不另建锁脚本、manifest、检查点、原文补件、ACK 审计包或阶段 RUN。没有登记设施时，在既有主 RUN 留一条已就绪角色的旧/新 ID 映射即可。原值已变化或登记写入失败时保留实际状态，不覆盖、不宣称切换成功；已创建的新 ID 保留供后续确认，不重复建页。
5. 新页仅回复“XX·角色已就绪，等待任务。”；Skill 无法读取则一次报告实际缺口，不假称就绪、不重复建页。失败页尚不承接业务，由创建方保留失败状态；成功页不为其他页失败重做。无 CONTINUATION_ACK、旧页 read_thread、总监复核、交接子智能体或向旧页发送收尾通知。登记后的旧页不再接新业务；保留或归档按已有明确授权执行，旧页已归档不影响本分支，不为补通知解除归档。

当前只是待命，READY 仅表示本角色 Skill 已加载；不表示工程权限、合同批准或验收通过。有效业务合同的批准链、来源和历史回包字段不因换页改写。

### 10.2 01–05 未完成任务：保留简短进度

先到安全边界，防止同一工程任务或所拥有进程由两页并行接管；已经在执行的旧页只需留下本角色当前目标、合同/主 RUN 精确定位、已改文件、已完成验证与证据、剩余工作及下一步、原权限/预算/停止条件、在途回包与资源所有权。能引用现有进度就引用，缺项才补，通常不超过 10 行；必要时作为一个 CONTINUATION_CHECKPOINT 记入同一主 RUN，不另建多份交接包。

创建新页的初始任务只加载对应 Skill 和这份进度说明，给出简短接手结果后等待续作；暂不执行工程。创建方负责确认旧页已安全停下、不再接新业务，新页已加载成功且接住当前进度；随后核对活动登记仍为精确旧 ID，一次切换到新 ID，并在原进度记录或现有登记中留实际结果，不另建交接包。登记成功后，由创建方沿当前已授权任务向新页发送一次续作指令，再按原权限、预算和回包绑定执行；无业务授权就等待。新页未就绪、登记原值已变化或写入失败时，不覆盖登记、不向新页派发续作，也不自动恢复旧页或重复创建；保留具体状态待解决。只在进度说明缺关键事实或有真实冲突时定向补读，不默认读取旧聊天、要求双页通知或创建交接审查子任务。新页不得重复已完成且仍有效的修改、测试，也不能把未验证结果写成通过。

已有 RELAY 的来源、返回页、revision、context 及预算保持原绑定，不能伪装成旧执行方回包；确需更换绑定时由既有责任方按原协议明确处理。旧页仍有在途结果则仅作为原回包入口转交一次；只处理实际待转交项，不追加“已就绪”通知链。进程/资源不能仅靠复制 PID 转移所有权，未解决的具体交接条件如实保留，不自动恢复运行或终止他任务进程。

### 10.3 00·总监：必要的上下文同步

旧总监到安全边界后，在同一 MASTER_RUN 写唯一 CONTINUATION_CHECKPOINT，向新页提供不超过 20 行的检查点和精确 READ_FIRST。保留：用户目标及最新更正、当前状态、已完成证据和禁止重做项、推荐方向与理由、已否决方案及理由、用户偏好与未裁决问题、唯一 NEXT_ACTION、权限/停止条件、旧新/当前活动页 ID、在途 RELAY 及原返回页。等待反馈也是有效 NEXT_ACTION，不为待命制造工作。

新总监加载自己的 Skill，沿低 Token 入口读取当前所需规则、合同与检查点；已提供且未变化的内容复用。实际调用 read_thread 定向读取旧总监涉及当前目标、最新更正和下一动作的用户正文与可见结论；先在工具层过滤推理、长工具参数和无关输出。只有关键事实仍缺失才按游标补读；一次有界补读仍无法取得必要正文则如实记录 OLD_PAGE_REVIEW=INCOMPLETE，不伪称读过、不创建第三页或灌入完整历史。

新总监用简短 CONTINUATION_ACK 说明实际回读范围、理解的目标/决策、当前状态、下一步、禁止重做项和阻断。项目/身份/权限一致、必要回顾完成且没有关键冲突时登记 READY=TRUE，再按 NEXT_ACTION 继续或等待；冲突先以当前物理证据和用户最新要求裁决，不能机械照抄旧结论。登记只切换当前活动总监，不擅自改写已派发任务的原来源、返回页和批准链，防止重复派发或漏收回包。

旧总监冻结新业务，只处理列明的在途回包并向新页转交一次；按原 context 核对来源并去重。需要旧页实际收尾或处理在途结果时，合并一次通知；没有待处理事项且共享登记已明确完成时不额外唤醒旧页。收到过换页授权不等于收到归档授权；仅在明确获准、接手已完成且在途清空后归档精确旧页，否则保留为非活动历史。旧页已归档时不为就绪通知解归档或新开审批。

### 10.4 共用边界

- 模型选择沿用全局唯一表和用户当前覆盖，同批只读一次；显式传 model/thinking，不继承旧页或主任务。工具不支持的 service_tier 不伪造，运行态未暴露写 unknown；不为确认模型/服务层另发业务消息。明确设置失败或模型不匹配只停止该页业务，不自动换模型或重建。
- 当前角色、项目、下一动作和权限必须准确；页面创建/标题正确不证明工作完成。固定角色独立性、批准/revision、安全边界与验证预算保持不变。
- 空闲换页只记录一条必要活动页映射；只有总监或未完成任务需要检查点。不要让旧胶囊模板、历史批次说明或一般性的接单/回传要求重新触发空闲页完整交接。
- 本节优化是流程规则，节省多少额度需实际同口径证据；不得因静态配置完成就宣称省额比例或运行生效。
