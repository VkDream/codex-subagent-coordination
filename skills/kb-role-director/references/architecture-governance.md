# 轻量架构治理

仅在 `kb-role-director` 的架构门触发时读取。本参考帮助总监把架构判断变成一个稳定、可执行、可审查的里程碑合同；它不是独立阶段，不授权修改工程，也不要求每个任务画图或新增 ADR。

## 1. 触发与跳过

以下任一项实质变化时触发：

- 模块、进程、设备、服务或部署边界；
- 状态、数据、资源、后台任务或外部连接的所有权；
- 公共 API、协议、ABI、事件、序列化或数据库结构；
- 线程模型、生命周期、恢复、容错或长期运行策略；
- 新框架、关键依赖、数据存储、通信方式或外部系统；
- 需要迁移、双轨、切换、回滚或跨版本兼容；
- 性能、可靠性、安全、可维护性、可观测性等目标主要由架构决定。

不改变上述边界的局部修复、文案/样式、窄测试补齐和既定模式内实现应跳过架构门。

## 2. 架构决策胶囊

在当前里程碑合同中保持一份胶囊，不自动新建第二套文档：

1. **目标与业务驱动**：解决什么用户问题；最重要的约束和成功条件是什么。
2. **当前物理事实**：系统上下文、模块/进程/数据存储/外部系统、真实调用与数据流、现有所有者和已生效决策。历史图和旧 ADR 只能作为线索。
3. **质量属性场景**：用“刺激/前置环境 → 系统响应 → 可测阈值”描述本里程碑最重要的可靠性、性能、安全、兼容、可维护或可观测目标；只选择会改变方案的少量场景。
4. **可行选项**：保留现状通常也是一个选项。只列真实可实施的方案；证据不足的方案标记 `UNKNOWN`，不凑数量。
5. **权衡与风险**：比较正确性/安全、可靠性/恢复、性能/容量、兼容/迁移、可维护性、可观测性、交付成本和新依赖。指出敏感点、取舍点及最坏失败方式。
6. **决策与边界**：写清选定方案、拒绝理由、唯一状态/数据/资源所有者、依赖方向、公共接口、允许例外及禁止的平行路径。
7. **演进路径**：给出最小可回退步骤、兼容窗口、切换条件、失败回滚和旧路径删除门；避免没有退出条件的永久双轨。
8. **守护方式**：把每条重要架构规则映射为静态约束、架构测试、构建检查、运行场景、可观测指标或人工验收，并标明由哪个角色、在哪个证据层级验证。
9. **未知与重审条件**：哪些事实仍缺证据；出现哪些新事实、阈值越界或外部变化时必须回总监重新决策。

## 3. 轻量决策法

- **先发现再决定**：优先遵循当前有效且一致的架构；不能仅因某种模式更新颖就引入。
- **场景驱动权衡**：不问“哪种架构最好”，而问“哪种方案在当前高优先级场景和约束下风险最低”。
- **可逆性定投入**：容易回退的选择快速、低仪式；涉及数据迁移、公共协议、硬件或生产切换的难逆决策需要更强证据和前审。
- **增量演进**：优先小步替换和明确退场条件；禁止未经合同批准的大重写、微服务化或双技术栈长期共存。
- **所有权先于分层名称**：每个状态、资源和写入路径必须有唯一责任方；名称漂亮但所有权不清不算架构完成。
- **接口杠杆而非层数**：优先让小而稳定的公共边界承载较大的内聚能力；新增一层若没有隐藏复杂度、集中策略或减少调用方协调，就不是架构收益。
- **局部性降低协作成本**：让状态、错误、资源生命周期和对应策略尽量在同一所有者附近闭合，避免一次业务变化跨越多个只转发的层。
- **删除检验与公共验证边界**：若删除一个抽象不会改变可观察行为、所有权或依赖压力，应质疑其必要性；重要架构规则应能通过公共边界或运行指标验证，不能只检查内部命名和源码形状。
- **规则必须可验证**：无法映射到证据的“必须分层”“保持解耦”等口号只能作为偏好，不能作为 PASS 条件。

## 4. 六角色分工

| 角色 | 架构职责 | 不得做 |
|---|---|---|
| `00·总监` | 拥有决策胶囊、权衡、边界、演进和重审条件 | 修改工程、替角色自证 |
| `01·诊断` | 交付当前架构事实、调用/数据流、所有权、约束和质量场景 | 用猜测替总监选方案 |
| `02·开发` | 按选定方案实现，并建立合同授权的守护证据 | 暗改边界、引入第二事实源 |
| `03·审查` | 独立审查决策完整性与实现一致性 | 代替总监作新架构决策 |
| `04·修复` | 批量修正已确认的架构漂移 | 借修复机会重新设计系统 |
| `05·验证` | 在授权层级执行质量场景和架构守护 | 用静态图或开发自测冒充验收 |

## 5. 外部资料取舍

- [eligapris/software-architect](https://github.com/eligapris/software-architect)：吸收“Discover → Diagnose → Decide → Document → Defend”、一致性、边界、渐进演进和 fitness function；不运行其脚本，不照搬“一项目一种 ORM/API”等绝对规则。
- [muthub-ai/c4-skills](https://github.com/muthub-ai/c4-skills) 与 [C4 官方模型](https://c4model.com/)：吸收“C4 说明系统是什么、ADR 说明为什么这样选”和按 Context/Container/Component 逐级展开；只有图能消除关键歧义时才要求绘制。
- [SEI ATAM](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/)：吸收业务驱动、质量属性场景、风险、敏感点和取舍点；不照搬需要多日团队会议的完整流程。
- [MADR](https://adr.github.io/madr/) 与 [Microsoft ADR 指南](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)：吸收选项、结果、正负后果、证据和重审条件；本地默认写入唯一合同/主 RUN，项目已有且获授权的 ADR 体系才另行维护。
- [obra/superpowers](https://github.com/obra/superpowers)：吸收根因优先、计划与可验收交付物对齐、新鲜证据先于完成声明；拒绝其固定 Git/worktree、逐微任务、强制子代理和重复验证要求。
- [mattpocock/skills 的 codebase-design](https://github.com/mattpocock/skills/blob/main/skills/codebase-design/SKILL.md)：吸收小接口承载大能力、局部性、删除检验和公共测试边界；不照搬术语禁令，也不引入其配套 Git、子智能体或报告流程。
- [IBM solution-architect](https://github.com/IBM/ibm-watsonx-orchestrate-adk/blob/main/skills/solution-architect/SKILL.md)：只吸收业务问题到技术边界、实施和验收的可追踪性；不要求生成三份长文档，也不引入其 AI/Watsonx 专用结构。
- [GitHub awesome-copilot 的 repo-architect](https://github.com/github/awesome-copilot/blob/main/agents/repo-architect.agent.md) 面向 Copilot/OpenCode 项目脚手架，不是通用软件架构师，因此不并入总监职责。
